| H1 | `words = line.split(" ")` at `fertility.py` L62. Sample files contain consecutive ASCII spaces: eng L7 `books  in`; hin L10 `किताबें  अलमारी`. Python `str.split(" ")` inserts empty strings between consecutive separators; `str.split()` with no args does not. | Word count is inflated by empty "words," so tok/word is biased **down**. If empty tokens are more common in one language sample than the other, the **hin/eng fertility ratio** is also biased. This would be a genuine implementation defect relative to the usual meaning of "words" (whitespace-delimited tokens). | implementation bug | med → **HIGH** (confirmed bug; 2 d.p. table cells shift) | Isolated: on the same loaded lines, count `split(" ")` empties per language; recompute fertility with `split()` vs `split(" ")`; report absolute and % change in eng, hin, and hin/eng ratio. Do not edit `starterkit(1)/`. Copy script to `partA/scripts/` if needed. |
| H2 | Corpus value is `sum(per_line_fertility)/n` (`fertility.py` L64, L66–L67), i.e. unweighted mean of per-line ratios, not `sum(len(tokens))/sum(len(words))` over the corpus. Same for tok/char (L65, L67). | Mean-of-ratios ≠ ratio-of-totals whenever lines differ in length or fertility. The printed 1.27 / 7.45 / 5.89× may not match a corpus-level tokens/words figure the report's "per request" language implies. | aggregation bug | med → **MED-HIGH** (real delta: ENG −0.95%, HIN −0.61%, ratio +0.35%; 2 d.p. cells differ) | Same encode/preprocess; compute (A) current mean-of-ratios, (B) total tokens / total words, (C) total tokens / total chars; compare A vs B (and tok/char A vs C) for eng, hin, and ratios. |
| H3 | `line = line.lower()` before `encode` (`fertility.py` L59–L61). Comment L59: "so casing doesn't add noise." GPT-2 BPE is case-sensitive. English sample has mixed case (e.g. eng L1 `Bengaluru`, L6 `NASA`). Hindi sample is Devanagari (case fold often a no-op). | Lowercasing changes English token counts more than Hindi, so it is **not** a noise-free, language-symmetric preprocess. Direction/magnitude of the hin/eng gap vs mixed-case encoding is unknown until measured. | preprocessing | med → **HIGH** (confirmed: ENG −2.84% fertility, HIN 0.00%, ratio widens 5.89→6.06×) | Ablate: identical pipeline with vs without `.lower()`; record token counts and both metrics per language; % change in hin/eng fertility. |
| H4 | `unicodedata.normalize("NFC", line)` at load (`fertility.py` L49), before lowercasing and encode. Comment L48: "some corpora are messy." | NFC can merge combining marks (relevant for Devanagari) and change both `len(line)` and BPE pieces. If these files are already NFC, the call is a no-op and the numbers will not move. | suspicious-but-maybe-fine | med → **LOW** (harmless on this sample: 0/20 lines changed; metrics identical under NFC/NFD/raw) | Compare metrics under NFC vs NFD vs no normalize on the same bytes; also count how many sample lines change under NFC. If zero lines change and metrics match baseline, treat as harmless on **this** sample (not a general proof). |
| H5 | `chars = len(line)` (`fertility.py` L63) after lowercasing. Python `len` on `str` is Unicode **code points**, not grapheme clusters, not UTF-8 bytes; spaces and punctuation are included. | tok/char is not "tokens per written character" in a linguistically stable sense. Hindi vs English `len()` can differ for reasons other than "tokenizer fertility" (combining marks, punctuation, spaces). Using it as a serving-cost proxy is a conceptual mismatch even if the code matches the comment. | conceptual metric problem | med → **HIGH** (confirmed: tok/char ratio 7.0× cp-based vs 10.86× grapheme-based — 55% gap) | On the same strings: compare denominator `len(s)` vs UTF-8 bytes vs grapheme-cluster count (e.g. regex `\X`); recompute tok/char and hin/eng ratios. Record whether ranking/ratio is stable. |
| H6 | REPORT_v0 L19–L20, L27–L28: tok/char "1.579 vs 0.226 = 7.0× … confirms the per-word number"; "the two metrics agree, so the result is robust." Phase 1 stdout: fertility ratio printed **5.89×**; printed-table tok/char ratio 1.579/0.226 = 6.986… . Both metrics share per-line `len(tokens)` (`fertility.py` L64–L65). | The two columns are **not** independent measurements. Algebraically, (tok/char_h)/(tok/char_e) equals (tok/word_h)/(tok/word_e) only if chars/word is the same in both languages (up to the mean-of-ratios vs totals distinction). Treating 7.0× as confirmation of 5.89× is a conceptual misuse of correlated metrics. The numeric gap 5.89 vs ~7.0 is an observation that they do **not** match at report precision; whether that is "robust agreement" is the hypothesis to test, not a finding here. | conceptual metric problem | high → **HIGH** (unchanged; Phase 3 H5 data confirms the metrics share a numerator and differ by chars/word factor) | Derive chars/word (or mean chars and mean words per line) per language from the same `analyze` loop. Show whether fertility_ratio × (chars/word_h)/(chars/word_e) recovers tok/char_ratio. State explicitly they share a numerator. |
| H7 | REPORT_v0 L21–L23: root cause is more Unicode characters per word; "any tokenizer will struggle"; "property of the script, not the tokenizer." The v0 script only loads one tokenizer per run (`fertility.py` L82) and REPORT used only `gpt2` (L8). | This causal claim is **not identifiable** from the v0 design: script vs tokenizer is a confound the experiment never crossed. "Any tokenizer" is an extrapolation. A large hin/eng gap under gpt2 is compatible with tokenizer mismatch, script properties, metric artifacts (H1–H5), or all three. | conceptual metric problem | high → **HIGH** (unchanged; Phase 3 confirmed H1-H5 metric artifacts exist; tokenizer comparison deferred to Phase 4) | Minimum identifying contrast: **same corpora and same metric code**, at least one Indic-aware tokenizer (e.g. `hf:` MuRIL / IndicBERT / NLLB SPM) vs `gpt2`. If the gap shrinks a lot, "not the tokenizer" is weakened; if it does not, still do not conclude "script" without controlling H1–H5. |
| H8 | Only tokenizer in REPORT_v0 is `gpt2` (L8); CLI default `--tokenizer gpt2` (`fertility.py` L79); non-`hf:` path is `tiktoken.get_encoding(spec)` / `enc.encode` (L34–L38). Reject/accept by measuring both ratios; not by asserting "gpt2 is bad." | conceptual metric problem | high → **HIGH** (unchanged; deferred to Phase 4 — tokenizer comparison not in Phase 3 scope) | Same inputs as Phase 1; run `gpt2` vs `hf:<indic-aware repo>` through identical `read_lines`/`analyze` (copy under `partA/scripts/`).
